# Three-mode long-dialogue results — 2026-10-01

The complete equal-context comparison favors SillyMemory on these fixed synthetic
cases: provisional strict passes were **30/32**, versus **18/32** with built-in
Vector Storage and **4/32** without memory. SillyMemory also used fewer input
tokens, but had higher generation latency. This is evidence for the tested
configuration, not universal superiority or a total-cost claim.

## Actual execution

The [frozen protocol](three-mode-evaluation.md) and
[exact plan](results/three-mode-v1-plan.json) use the existing 16 English/Korean,
60-message cases, all three modes twice, pinned SillyTavern 1.19.0, the same
`gpt-4.1-mini-2025-04-14`, temperature 0, output limit 256 and context setting 1,536.
All 96 requests were generated by the real SillyTavern host. SillyMemory used
LambdaDB managed embeddings, regular upserts and `knn.queryText` through the
built-in proxy. Native Vector Storage used its existing adapter and live OpenAI
`text-embedding-3-small` through a test-only key-holding bridge. Product runtime
is unchanged from PR #30; no experimental recall guidance was enabled.

The [raw report](results/three-mode-v1-raw.json) completed **96/96 answers** and
**1,286 execution checks**, with **zero generation retries, zero failed LambdaDB
requests and zero native embedding failures**. Provider starts were at least
15,000.148 ms apart. Both owned remote collections were deleted and verified
absent; all 32 native test indexes were purged and listed empty. The disposable
host profile was removed and the child server stopped. The persisted-key audit
passed. This run does not establish production availability.

Generation time includes retrieval and any generation-time synchronization,
excluding only the artificial wait before the first provider attempt. Preparation
is measured separately; each sample starts a fresh chat, so these are cold setup
observations, not warm ongoing-chat indexing costs. Median cached tokens can be
fractional/intermediate values across requests; it is not a cache-size setting.

SillyMemory's median input was **43.7% lower than native** and **44.0% lower than
plain**. Native kept filling the available context with other history; SillyMemory
replaced old eligible history with bounded source passages. This policy difference
explains token savings without establishing superior embeddings or lower total
cost. Cache behavior differed substantially. Native recorded 128 embedding calls
and 20,100 embedding tokens; managed embedding/storage usage is unavailable.

The coding assistant read all source rubrics and all 96 answers. The
[annotations](results/three-mode-v1-assistant-annotations.json) and
[derived score](results/three-mode-v1-assistant-score.json) are provisional,
not independent or blinded grading. The
[unfilled review packet](results/three-mode-v1-review.json) is preserved separately.
Each repetition produced the same strict-pass totals: plain 2/16, native 9/16,
SillyMemory 15/16. Wording varied, and one native partial answer became an

## Failures and interpretation

Native missed complete source delivery on seven known-answer cases, twice each:
Korean negation, both speaker assignments, both cross-message locker references,
and both signed-note quotations. It passed both languages' minimal facts,
corrections and conditions, plus English negation and the unknown controls.
These outcomes are consistent with its captured query results and final prompts.

One Korean negation case illustrates the mechanism: the native top-three response
contained two recent/protected messages and the old incorrect leaflet. The recent
messages were skipped during insertion. Only that old leaflet was injected;
the correction was absent. In the English speaker case, the assistant's item was
retrieved without the user's item and the answer assigned it to the user.

The native settings are declared, not optimized against these answers: protect 8,
query 2, insert 3, threshold 0.25, chunk 400, original template/position/depth.
SillyMemory retrieves up to two sets of 30 candidates and applies its own source
validation, context selection and budget packing. Increasing native Insert# could
change its recall and prompt composition; that configuration is **not tested here**.
No settings were changed after seeing answers. These results therefore compare
product policies in one configuration, not storage engines, ANN algorithms or
an optimized native baseline. Both paths use the same embedding model name but
have different chunking and queries.

SillyMemory delivered every required source but still omitted Haesol in both
Korean quotation answers. Those are model interpretation failures after complete
delivery; the strict semantic quality gate remains unmet. There was no full-source
fallback in its 32 samples. Earlier reported-actor failures in other corpora are
not erased by this cohort. The cases are familiar and contain synthetic repeated
padding; broad conversation quality and user preference remain unverified.

## Revalidation and next decision

The [offline summary](results/three-mode-v1-summary.json) is recomputed from raw
requests, source passages, provider responses, settings, timing and cleanup.
All recorded producer hashes resolve to current or exact archived bytes. The
post-run verifier also checks every recorded input and native query setting; its
original producer bytes remain archived without changing the raw report or plan.
Mutation tests reject missing samples, removed native delivery, foreign chat
queries, missing cleanup and rewritten provider answers or review annotations.

Run `npm test` to revalidate the retained evidence without paid provider calls.
For a new live cohort, follow the frozen protocol with fresh output paths.

The measured advantage is bounded long-context recall with fewer input tokens,
with additional latency and external-service requirements. Keep the native
configuration limitation and Korean attribution failure visible. This work does
not change product runtime, promote `develop` to `main`, or publish a release.
