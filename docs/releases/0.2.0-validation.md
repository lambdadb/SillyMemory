# 0.2.0 installation and upgrade validation

## Decision and bounds

Determine whether the current candidate can be installed and upgraded through
SillyTavern's Git URL UI while preserving settings and safely rebuilding old
shared memory into isolated chat collections. Stop after the default installation
run and one successful live lifecycle run, or document a concrete blocker.

Use SillyTavern 1.19.0 at `06bde939fb1e9c4c8d8641d810f0a916b5bce127`, an
isolated host/browser profile and synthetic history. Live mode permits at most
four owned collections per attempt and no generation-model calls. Any failed
attempt requires confirmed cleanup before retry. Retain detailed outputs locally;
this is recurring release acceptance, not a new answer-quality benchmark.

## Results

Completed on 2026-10-03 against candidate
`b5d1e83846546e1afab29067fc7843c9c5e5397c`.
Public main stayed at `b55b78f28feb769683da723206bf3b37c83ec04b` (published
`v0.1.0`). Both final runs installed that exact main through **Install extension**,
then used the actual **Update** UI to pull `chore/prepare-020-release`.

The disposable installed clone tracks the candidate from a common ancestor whose
tree equals the installed main tree. This avoids divergent long-lived branch
history without changing installed files. It verifies a real GitHub clone/pull;
it is not evidence of a published main-to-main upgrade.

The live run starts on 0.1.0 with 18 synthetic messages, including one long message
that spans multiple chunks. Recent retention is 14 messages and memory budget
600 tokens to prove non-default settings survive update. The four collections
are the transport gate, old shared memory, upgraded parent and native branch.

After update, the old pointer and full remote documents are unchanged. First
sync creates a distinct collection whose documents exactly match the current
boundary-aware producer. Rename retains the collection; native branch creates
another, and editing its old fact removes obsolete chunks while preserving the
parent and shared data. Managed queryText through the actual interceptor recalls
the branch's new fact and preserves recent history. Current-chat deletion is
confirmed by API 404 before checking unaffected collections. Reload/key re-entry
reuses the parent with no fifth creation. All-owned deletion removes both the
legacy and new collections before fallback cleanup. Every recorded collection
is confirmed unavailable, and the isolated profile is removed. Keys are absent
from persistent browser and host settings; no uncaught page errors occurred.

The interceptor invocation uses a synthetic final-prompt event to release its
reservation. It is not a full provider generation. The separate retained delivery
fixture covers actual host prompt dispatch; no new answer quality or model
reliability claim follows from these release checks.

## Failed attempts and recovery

- Attempt 1 reached legacy-data preservation, then timed out because the runner
  did not reselect the saved character after update/reload. Cleanup completed.
  The runner now explicitly selects the character and awaits its saved history.
- Attempt 2 reached branch editing and managed recall, then timed out attempting
  a deletion control after native navigation. Its unused one-shot dialog handler
  collided with the cleanup handler, causing an unhandled rejection. The normal
  report remained `{}`; this is incomplete evidence, not a passing run. Its
  durable ownership record survived. A one-off Node client recovery independently
  verified all four recorded collections absent and removed that isolated profile.
  That direct-HTTPS cleanup is not counted as proxy integration evidence.
- The final runner opens the settings panel before deleting, uses one dialog
  handler, records failures before cleanup, and preserves failed cleanup records.
  Attempt 3 completed through the real proxy, including deletion checks before
  any fallback cleanup. No runtime fix, quality retry or generation call was made.

## Release decision and limits

Installation/lifecycle acceptance is complete for this pinned host and synthetic
profile. Existing historical quality results and limitations are linked from the
[release notes](0.2.0.md). They are not repeated or relabeled as a fresh evaluation
of this release. In particular, the new chunker does not have a demonstrated
answer-accuracy gain and hybrid search is not shipped.

Main promotion, tag and pre-release publication remain separate approval steps.
The next release decision is review of the preparation PR, followed by choosing
an approved changelog date and the develop → main promotion. Main users still
receive 0.1.0 until that promotion. This is not a stable-support commitment.
