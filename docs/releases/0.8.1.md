# SillyMemory 0.8.1 — experimental pre-release

Prepared release candidate, currently **Unreleased**: the changelog entry is
dated only after the external verification on `develop` completes. Preparation,
main promotion, version tags and GitHub Release publication are separate steps.
Confirm publication in
[GitHub Releases](https://github.com/lambdadb/SillyMemory/releases).

Supported host: SillyTavern 1.19.0 at
`06bde939fb1e9c4c8d8641d810f0a916b5bce127`, with Chromium.
Other host versions and browsers remain unverified.

## Why this release

Two reports from real use of 0.8.0 on the same day:

- Turning memory on in a new chat sent seven LambdaDB requests in about 0.3 s.
  The seventh, a collection metadata read, returned HTTP 429 and the chat
  stopped at **Needs attention** even though nothing had been written. A manual
  retry 18 s later succeeded. SDK retries are disabled by design, so the 429
  surfaced immediately.
- After clicking **Turn memory on in this chat**, the panel showed **Ready** for
  about 0.65 s before synchronization began. A message sent in that window was
  stopped with **Reply stopped**, because the activation was still saving.

## Changes from 0.8.0

- **HTTP 429 is retried briefly** (#135). A request LambdaDB rejects with 429 was
  not processed, so the same read or write is sent again at most twice, after
  `Retry-After` when the browser can read it or after 1 s then 2 s, inside the
  same 15-second deadline and cancellation. 5xx, timeouts and network failures
  are still not retried; failures still stop with an explicit status.
- **Fewer metadata reads when a chat's memory is created** (#135). The created
  collection and branch are verified from their 201 responses, and the sync or
  generation that follows in the same preparation does not read the collection
  again. A new chat sends four requests instead of seven; a repeat sync sends
  two instead of three. Conflicts (409) still trigger a fresh ownership read.
- **Activation status** (#136). While **Turn memory on in this chat** is saving,
  the panel reports **Updating**, not **Ready**. A message sent during the
  activation, or during another memory action, waits for it and then prepares
  the reply. If the activation fails and leaves memory off, the reply stops with
  the activation error instead of silently using native history.
- **Sync now removed** (#136). It ran the same synchronization as **Retry
  synchronization**, which still appears after a failure; synchronization also
  runs on every message, edit and chat change. Failure messages now name
  **Retry synchronization**.
- **Upsert batches of 200 documents instead of 50** (#137). In a live
  measurement with the production schema a request cost about 0.45 s plus
  5.5 ms per document, so the first indexing of a long chat takes about half the
  time. Ordinary chatting still sends one request per displaced message pair.
  See [upsert batch size](../upsert-batch-size.md).

## Installation, update and rollback

Install the repository URL with an empty branch field to follow public main.
Reviewers can enter the preparation branch in the branch field, or `develop`,
in an isolated profile before main promotion. Update through Extensions →
Manage extensions → SillyMemory → Update, then reload. Update follows the
installed Git branch, not the newest tag/Release. Automatic updates remain
disabled; no build step or server restart is needed.

**Updating from 0.8.0:** nothing to do after the reload. There is no settings or
data migration; the saved key, each chat's saved on/off choice and saved memory
are unaffected. Collection schema, ownership tags, chunking, search policy,
managed embeddings/reranking, recent-history alignment and token budgets are
those of 0.8.0. The extension manager shows version 0.8.1.

**Updating from 0.7.x or 0.6.0:** the 0.8.0 notes apply unchanged: chats that
were on come up off and must be turned on again (saved memory is reused), and
frozen memory snapshots are no longer available.

To roll back, disable memory and pin published `v0.8.0` using the
[release procedure](../../RELEASING.md#user-updates-and-rollback). Rollback does
not undo remote writes or deletions; 0.8.0 reads memory written by 0.8.1 because
the schema and documents are identical.

## Acceptance and limits

See [0.8.1 acceptance](0.8.1-validation.md) for the inherited evidence of the
three merged PRs, the installation/update acceptance and the checks that remain
pending. This preparation adds no paid-provider or answer-quality experiments.

Known limits of this release:

- The LambdaDB request-limit value and unit, and whether its 429 responses carry
  a readable `Retry-After`, are unconfirmed. A chat with a long existing history
  still sends a listing and upload burst at activation, which a low burst limit
  could reject; the retry covers short waits only.
- The 200-document batch evidence comes from one project at one time of day with
  synthetic English text, with no plan-quota or congestion data.
- Group/tool conversations, concurrent multi-device writers and non-Chromium
  browsers remain unsupported or unverified. The complete-query 8 KiB limit and
  recent-history limits still apply. Previewed memory, prompt verification and
  token estimates do not establish answer correctness or provider receipt.
