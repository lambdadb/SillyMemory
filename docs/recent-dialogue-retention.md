# Recent dialogue retention

## Product decision

Retain at least five recent eligible plain-text messages through the active input,
with their native roles and source order, regardless of retrieval or the previous
answer's request status. Include the entire unresolved clarification span when it
starts earlier. Normal alternating dialogue therefore retains the preceding two
user/assistant exchanges plus the current input. If the window starts at an
assistant reply with an adjacent eligible user input, include that user too.
After a normal reply this keeps six messages, so the next input displaces a whole
input/reply pair with one write instead of two partial writes. Each message retains
its own chunks and IDs; pairs are grouped in a request, not merged into documents.
Blank/ineligible turns do not
consume slots, and replacement reply suffixes are never retained.

This is a usability and source-delivery contract: an ordinary follow-up should
not depend on rediscovering the immediately preceding exchange. It is not a claim
of independent benchmark superiority or proof that five messages is universally
optimal. The separate confirmation quality-improvement gate is inconclusive;
engineering adoption rests on the concrete failure/replay and delivery invariants,
with no observed new regression in the frozen controls.

Ordinary storage now archives completed eligible messages only after they leave
this five-message window. Upload displaced chunks immediately, grouping whatever
is ready at the same synchronization in existing batches of up to 50 documents.
There is no queue waiting for five displaced messages. The only ordinary extension
is the one user message needed to avoid splitting its adjacent reply. Checkpoints synchronize the complete completed transcript.
Ordinary retrieval uses the two most recent eligible messages through the query
anchor, normally the preceding assistant reply and current user question, with
roles/order preserved in one request. A longer unresolved span takes precedence.
No rewriting model or additional search is added. Vector/lexical prefilters and
local selection still exclude fully retained positions before ranking/budgeting.

The original evaluation below used unchanged completed-history storage and
current-question queries; its scores do not establish this follow-up's quality.
The separately bounded query/storage comparison is recorded at the end.
Managed embeddings, Bayesian English/Jev, k=100/candidateSize=100/size=50,
800-code-point boundary chunks and the 4,096-token memory budget remain unchanged.
The quarter-context memory cap remains. Recent/pending source is outside that
memory budget but within the host's total context and final delivery guard. Large
recent messages can exhaust context even with no recalled excerpts. The default
guard then stops generation with recovery guidance; it does not silently shorten
the five-message window. Disable memory to use ordinary native history.

## Original Retain 5 evaluation protocol

The [input lock](recent-dialogue-inputs.json) records two discovery dialogues and
twelve confirmation dialogues, with the existing 24 clarification dialogues as
regression controls. Inputs/references were fixed before the first paid answer.
The same Sol/low model, pinned SillyTavern 1.19.0, 32,768 context and 4,096 output
limit apply to both conditions. Recent retention also changes the exclusion range
for fully retained source, as required to prevent duplicate memory; it is not a
comparison of query construction, storage cadence or search limits.

Histories come from the already-consumed checksum-locked LongMemEval-S dataset.
Added aliases, reminders, proposed books and follow-ups are controlled derived
conversations, not claims that these additions occurred in the original benchmark.
Identical frozen assistant prefixes are controlled schema responses through native
generation: ordinary prefixes end with `answered`, regression prefixes open
`needs_clarification`. Every final comparison reply is generated by live Sol
through the native host with real managed LambdaDB retrieval. The paid comparison
is non-streaming; streaming is covered by the local native lifecycle/delivery checks. This does not test
autonomous classification of the initial prefix or LLM-emulated user behavior.

All final answers were inspected by the agent against the frozen target and
instruction, with original responses/prompts retained. No paid judge, selective
quality retry, blinded audit or independent human review was used. Status and
literal matching are secondary signals, not factual correctness certificates.

The two concrete failures asked to repeat the immediately preceding book title
in uppercase and degree subject in lowercase. With current-input-only generation,
the book text was absent and Sol asked which text; the degree response instead
repeated unrelated retrieved advice. The Retain 5 replay produced exactly
`THE SEVEN HUSBANDS OF EVELYN HUGO` and `business administration`, using the
preserved source. These results establish the local mechanism, not broad recall.

The remaining confirmation failure names a previously created Spotify playlist
as Project P, then asks its original name. Both conditions return 50 documents
without the original name, Summer Vibes, and the name never reaches selected
memory. Retain 5 preserves the alias correctly but cannot supply missing historical
evidence. This is a candidate/query issue, not current-window loss or token
packing. This demonstrated failure motivates the separate Query 2 comparison below.

The coupon reference expects Target. Both prompts contain the coupon statement
and nearby Target discussion but no explicit sentence connecting that redemption
to Target. The candidate's added recent source is unrelated workout advice; no
new linking evidence is recovered. Sol abstains in one condition and asserts Target
in the other. Preserve the reference-score difference without claiming a grounded
quality improvement from it. The other 23 controls retain their requested facts,
absence behavior, cancellation and terminal-status semantics.

Median provider-reported input tokens in the new twelve-case cohort are
4,392.5 versus 4,940 (+547.5, about 12.5%). In the regression cohort they are
4,372.5 versus 4,808.5. These are selected native prompts, not token savings versus

### Active-input review correction

Recent retention now uses the actual native generation position, independently
of query eligibility. Normal/Continue/Impersonate use the final source position;
regenerate/swipe use the latest user position, including blank or ineligible inputs,
and exclude replacement replies afterward. An empty source has no retained input.
Five eligible text turns remain protected before an active special/blank input;
special content keeps the existing native handling. Retrieval also intersects the
recent boundary with its existing eligible-query boundary, so this correction
cannot broaden the candidate range or search the query's own source.

Unit and native-hook regressions cover file/media/tool metadata, a blank actual
native generation, response preservation and replacement exclusion. They do not
certify real uploaded-file or multimodal provider processing. The earlier paid
comparison used nonempty eligible normal inputs, where the actual position equals
the old query anchor; its query/window paths are unchanged by this correction.
No paid quality rerun is needed or claimed. Original evidence remains preserved.

Final correction validation: 377 units; runtime/script/test syntax, release and SDK
checks pass. With the same pinned host, port 18136 and tag
`recent-retention-anchor`, the browser suite passes 86 checks and the fault suite
passes 91. `scripts/prompt-delivery-smoke.mjs` with output
`artifacts/prompt-delivery-recent-retention-anchor.json` passes all 17 cases plus
assembly/overlap. No page errors or remaining emulator collections. These supersede
the earlier runtime shape checks; original paid quality receipts remain unchanged.


## Query 2 and immediate archival follow-up

The user requested two changes after the original retention decision: include the
preceding eligible message in ordinary retrieval, and avoid embedding the recent
five until they leave the raw window. The later decision explicitly rejected a
five-message write queue: it would require retaining additional unsent source
(and increase generation input), or leave a source gap. The current runtime
implements immediate displacement, not batching by five messages.

Ordinary background synchronization and generation preparation use the same
recent boundary. All currently displaced chunks are reconciled in upsert batches
of at most 50 documents. IDs, local-source validation, delete-before-upsert,
acknowledgement, uncertain-write reload recovery and consistent reads remain.
Recent edits/swipes are uploaded only when the source leaves the window; already
archived edits/deletions reconcile normally. Regenerate/swipe storage ends before
the five-message window through the actual user input, excluding replacement
suffixes. A longer unresolved span can still be stored outside the recent window,
but remains fully present and excluded from both search legs. Checkpoints omit the
ordinary archive boundary and synchronize every completed eligible message before
confirming the snapshot. No state is kept solely in a volatile write buffer.

Query 2 means one complete role-labelled query, shared by vector, lexical and Jev
stages. Normal alternating dialogue includes the previous assistant reply and the
current question. Blank/ineligible source is skipped; a single eligible message
uses its plain text. Continue/Impersonate use their existing anchor and one prior
eligible message. Replacement reply suffixes never enter the query. A fresh
request root at the active input does not disable Query 2; an earlier pending root
uses its entire dialogue instead. There is no rewriting model, extra search,
truncation or separate previous-message reranking. The combined input still has
the existing 8 KiB query limit, so two long messages can stop generation sooner
than a question-only query. The UI reports the limit rather than dropping context.

### Cost boundary

Before pair alignment, this changed write timing without guaranteed write-request savings. With exact
five-message retention, a user input and its subsequent assistant reply can each
move one old message across the boundary, producing two small upserts per exchange
instead of the former completed-pair upsert. The initial archive excludes recent
messages, and repeated changes while still recent avoid embedding obsolete
versions. Two messages displaced at the same synchronization share one upsert
when their chunks fit the existing 50-document batch. This historical exact-five revision kept ordinary raw generation at five rather
than growing it to nine. The subsequent pair-boundary refinement below keeps five
at a normal new user input and six after a reply.

LambdaDB documents a 50 KB minimum per upsert and a fixed 100 KB write charge per
delete request. Fewer submitted documents therefore do not alone prove a smaller
bill. These are documented billing rules, not measured account invoices; see
[Understanding costs](https://docs.lambdadb.ai/guides/costs/understanding-costs).
Query 2 also sends more input text to managed embedding/reranking than a question
alone; one request does not mean unchanged inference-token usage. It adds no
query-rewriting LLM call and no additional raw generation messages.

## Complete-pair archival refinement

After the Query 2 comparison, the user chose to group a completed input and reply
in one write without waiting for five displaced messages. The current boundary
starts with the recent-five eligible window, then moves back exactly one source
position only if that first message is an assistant reply with an adjacent eligible,
nonblank user input. Both storage and raw retention use this same boundary. This
keeps five at a normal alternating new user input and six after the reply, avoiding
a source gap or a second write immediately after that reply. An initial greeting,
consecutive same-role messages, blanks, special/incomplete source are not invented
into pairs. Their existing eligibility, native handling and source validation stay.
A longer pending clarification span remains complete.

Pairs share an upsert request, not a document: per-message IDs, text chunks,
metadata, roles, positions and the existing 50-document ceiling are unchanged.
Large pairs can require more than one request. Archived edits/deletions, insertion
renumbering, uncertain writes and explicit retries can also require extra writes;
this is not a universal one-request-per-turn guarantee. Checkpoints still
synchronize the full completed transcript. Query 2, search/rerank limits, managed
embeddings, the memory budget and current-search-only injection do not change.
Continue/Impersonate can retain six eligible messages and still obey final context
verification; this is an intentional one-message extension, not a nine-message
write buffer or a new setting.
